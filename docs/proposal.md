# OffNav 产品说明计划书

## 一、它解决什么真实痛点（对应 AI 场景价值 40%）

校招生找面经的真实处境：经验散落在知乎各个问题下，单次搜索只返回 10 条且无分页，前排常被营销号占据，用户没有办法判断哪条经验值得信。这个痛点必须靠知乎解决，因为只有知乎同时提供内容深度和**可信度信号**——`AuthorityLevel`（权威度）、赞同数、评论数。同类平台能堆面经数量，但没有这套社区沉淀出来的信任信号，OffNav 离不开知乎的数据。

OffNav 用 5 组关键词（如"面经""一面 二面""笔试 真题"）串行取材，实测一次真实运行从 34 篇去重原文里，按 `AuthorityLevel` 重排结构化出 7 个面试轮次（笔试/群面/一面/二面/交叉面/总监面/HR 面），且**丢弃数为 0**——每一条结论都能溯源，其中一条来自一篇 L4、2528 赞同的专栏。权威度分布是 L4 17 篇、L3 12 篇、L2 5 篇，说明重排确实把高权威内容筛了出来，不是简单堆量。

对知乎生态的实际价值，用同一次运行的数据说明：

- **内容质量**：34 篇检索池里被最终引用 16 篇，引用率 47%。重排是在筛选而不是堆量，被前排营销号盖住的高权威长文因此被提到用户面前。
- **效率**：这 16 篇原文被结构化成 7 个轮次、15 个主题、52 条考点。用户从"翻十几个问题、自己拼图"变成"读一张地图"。
- **回流**：52 条考点指向 16 篇不同的知乎原文，也就是**一次使用结构性地产生 16 个回流入口**。这不是产品声称鼓励回流，而是产出形态决定的：考点是索引，展开看细节必须点回原文。OffNav 不做发布、不留客，也做不到留客——开放平台根本没有发布写接口，产出只能是深链。

换句话说，OffNav 与知乎不是替代关系，而是把知乎已有的答案变成一条可导航的路径，走这条路的每一步都通向知乎站内。

## 二、怎么做的（对应创新度 25%）

三入口一内核：岗位导航（主打）、问题对照、背景匹配，共用同一条链路"知乎取材 → 权威度重排 → AI 结构化 → 证据链校验 → 深链回流"，三个入口只是取材关键词和呈现形态不同。

**证据链是产品的原子单位**：每条 AI 结论必须挂来源卡（标题、作者、权威度、赞同数、原文摘录、深链），四要素缺一不成立。**反编造的工程闸口**是这个主张真正落地的地方：`lib/prompts/base.ts` 的 system prompt 要求 AI 为每条结论回填引用的素材编号，`lib/core/evidence.ts` 的 `attachEvidence` 在服务端逐条核对编号是否真在检索池里，核不上的直接丢弃、不进入响应。界面上把"已丢弃 N 条无法回溯到来源的内容"这个数字直接显示出来——它不是隐藏的容错逻辑，而是产品对用户的一个可见承诺：你看到的每一条结论都经过了机器验证。这一条在真实运行里丢弃数为 0，说明约束不是摆设，是真的在跑。

权威度是唯一强调色：L1–L4 做成可见徽标并驱动整套配色，让"用知乎自己的信号重排"这件事在界面上直接看得见。有意的减法是问题对照页不做 AI 立场分析，只按权威度并排呈现，观点分歧留给用户自己判断，避免 AI 在众说纷纭的问题上给出一个看似圆滑实则武断的结论。

## 三、技术实现（对应完成度 25%）

架构：Next 15 App Router + React 19 + TypeScript + zod + Vercel AI SDK，PostgreSQL 部署在腾讯 CloudBase（新加坡地域）。

知乎开放平台用法与实测约束：

| 约束 | 实测结果 | 应对 |
|---|---|---|
| 单次搜索上限 | ≤10 条，`HasMore` 恒为 false，无分页 | 多组关键词串行取材扩池，实测 5 组关键词取回 34 篇去重原文 |
| 并发限流 | 5 并发请求中 3 个返回 `Code=30001 rate limit exceeded` | 改为串行请求，间隔 ≥400ms |
| 字段类型 | `AuthorityLevel` 是字符串而非数字 | 排序前强制转型，否则 `NaN` 会静默破坏排序 |
| 知乎知识库 RAG | 上传原文后检索返回的是服务端生成的整篇摘要，原文与单条来源归属全部丢失 | 判定不可用于证据链，未纳入主链路 |
| 发布写 API | `creator` 额度组四个接口全是 GET，且只认 Access Secret 本人身份，无法代表用户发布 | "一键发布回知乎"是伪需求，产出改为可复制文本 + 深链 |

缓存不是优化项而是能跑起来的前提：全部搜索结果按 `query_hash` 缓存 24 小时，评委反复体验不会撞到瞬时限流。生成模型默认用知乎直答（`zhida-fast-1p5`，验证过能返回干净的无代码块 JSON），但其 100 次/天额度是全租户共享，撞额度时自动降级到智谱 glm-5.2，并在界面上告知用户发生了降级，而不是静默换模型。

安全：OAuth `state` 为 256 位随机值，存数据库并绑定浏览器 cookie，单次消费；OAuth token 只留在服务端；`uid` 是 int64，解析前用正则从原始响应里取出再转字符串存储，避免 `JSON.parse` 静默丢精度四舍五入。

测试：90 个单元测试，覆盖证据链回填与丢弃、缓存命中/过期/失败不写入、额度降级的四种行为、OAuth state 防重放。

## 四、体验设计（对应产品体验与设计感 10%）

**移动端优先是刻意的产品决策，不是没做适配**。理由：目标用户在手机上刷知乎；而 OffNav 的链接被分享出去后，点开它的那次访问几乎一定发生在手机上——一个在手机上会横向滚动的页面，会在第一秒失去这个访客。

所以单列 feed 是设计基准而非降级形态，宽屏（≥1024px）是增强：来源池抽屉在宽屏下变成右侧常驻栏，形成「左边是 AI 结构化的结论、右边是原始素材池」的并置——这正是本产品反黑箱主张的界面表达。评委若在电脑上访问，看到的是这个增强版；若把窗口收窄到手机宽度，看到的是基准版。两者都是完整形态。证据链卡片默认折叠成一行，点开才展开原文摘录和深链，避免一条结论挂多张卡把页面撑爆。

配色取自知乎官方 ADS 设计令牌（品牌蓝 `#1772f6`、`Frame/99A`、`Frame/10A` 及对应文字灰阶），来自官方黑客松技能包提供的示例 CSS。诚实说明一个取舍：品牌蓝配白字对比度是 4.40:1，略低于 WCAG AA 的 4.5:1 门槛，所以正文链接换用压深一档的蓝色，品牌蓝本色只用在达到 3:1 门槛即可的大号主按钮上。10 组权威度徽标的背景配文字组合全部达到 4.5:1 以上。

## 五、已知边界（诚实交代）

- 知乎开放平台没有内容发布接口，"一键发布回知乎"不做，产出是可复制文本加深链，用户手动决定要不要在知乎发表。
- 知乎知识库 RAG 检索返回的是整篇文档摘要而非原文片段，会丢失单条来源归属，与证据链设计冲突，未采用。
- App ID / App Key 在提交项目时才生成，开发期 OAuth 登录只能针对 Mock 联调，真实登录要等提交后才能验证，手机端授权跳转知乎 App 再跳回浏览器的断链风险目前无法实测排除。
